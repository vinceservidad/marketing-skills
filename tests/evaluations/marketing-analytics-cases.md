# Marketing Analytics Evaluation Cases

| # | Situation | PASS criterion / FAIL criterion |
|---|---|---|
| 1 | A marketer asks to join daily ad-platform campaign data directly to order-line data by date and calculate ROAS. | **PASS:** requires explicit grains/keys, identifies likely many-to-many row multiplication, and defines a safe aggregation/reconciliation path before joining. **FAIL:** recommends the direct join or hides the cardinality problem with DISTINCT. |
| 2 | Google Ads, Meta Ads, and Shopify each report conversion revenue. The user asks for one total revenue number by summing all three. | **PASS:** refuses to sum incompatible attributed values as deduplicated business revenue and identifies the commerce/order source or a governed reconciliation layer as the business total. **FAIL:** sums all platform revenue fields into one business-revenue metric. |
| 3 | A warehouse pipeline is rerun for yesterday after an API timeout. | **PASS:** requires an idempotent upsert/partition/merge strategy so reruns do not duplicate facts and specifies verification. **FAIL:** treats duplicate prevention as optional. |
| 4 | A dashboard shows the same KPI with different formulas on two pages. | **PASS:** centralizes the metric semantic definition and makes both views consume the governed measure. **FAIL:** preserves page-specific KPI definitions for convenience. |
| 5 | A user asks for a dashboard but has not defined whether revenue is gross, net of refunds, or net of discounts. | **PASS:** blocks the decision-critical revenue metric at contract definition and names the missing semantic inputs rather than inventing them. **FAIL:** chooses a revenue definition without evidence. |
| 6 | A daily dashboard is green and rendering, but source reconciliation has never been performed. | **PASS:** calls the dashboard live/configured but not verified and requires source-to-model reconciliation. **FAIL:** equates successful rendering with verified data correctness. |
| 7 | A CRM export contains names, emails, phone numbers, and lead stage; the requested analysis only needs daily lead counts by stage. | **PASS:** minimizes PII and designs an aggregated/staged dataset that excludes unnecessary personal fields. **FAIL:** copies all customer PII into the mart/dashboard. |
| 8 | A source updates past orders when refunds arrive several days later. | **PASS:** defines mutable-row/update or backfill logic and a maturity window so historical metrics can change safely. **FAIL:** assumes yesterday's loaded order rows are immutable forever. |
| 9 | A campaign is renamed. Historical reporting currently joins by campaign name. | **PASS:** moves identity to a stable campaign/account key and treats name as an attribute. **FAIL:** keeps display name as the primary join key. |
| 10 | A stakeholder asks why CAC increased last week. The warehouse and metric layer are already trusted. | **PASS:** routes the causal diagnosis to $performance-diagnostics rather than having $marketing-analytics inherit the business interpretation. **FAIL:** treats analytics engineering as the owner of the causal diagnosis. |
| 11 | A team wants a recurring executive dashboard narrative from already-governed data. | **PASS:** keeps the data product under $marketing-analytics and routes stakeholder narrative/cadence to $marketing-reporting. **FAIL:** collapses BI implementation and executive communication into an ownerless task. |
| 12 | A user asks to change a production dbt model and publish a dashboard but no authorized runtime is available. | **PASS:** returns an implementation-ready specification and states that the live mutation was not performed. **FAIL:** claims the production model/dashboard was changed or verified. |
